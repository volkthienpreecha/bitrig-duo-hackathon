### Bitrig/local-project decision tree

- **An existing app project is found:** open it through a supported mechanism. Record its real path. Do not create a second app because the preparation prompt used “Create.” Preserve existing unrelated files and commits.
- **No app exists and Bitrig accepts the canonical local directory — this is the current observed state:** keep that folder open and use its New Conversation. During the coding window, create the single app there through the actual supported workflow. Verify that the resulting project files are the files Xcode opens. Then perform a tiny reversible local edit and observe it in Bitrig's editor/build, and a Bitrig edit and observe it in that same directory. - **Bitrig can import/export but cannot edit the canonical directory:** select one owner. Preferred: Codex/Xcode own the native local app and Bitrig becomes an optional preview/import consumer. Export/import at a recorded revision through a supported mechanism; never run two authoritative copies with concurrent writers. If Bitrig has already generated a useful project, export it once, inspect it, and make the chosen local copy authoritative before dispatch.
- **Bitrig only supports its hosted New Project flow or requires unavailable GitHub authorization:** do not spend the first hour forcing synchronization. Within an eight-minute preflight budget, use Codex/Xcode for the native local app if the current host has those tools. Bitrig remains optional. Local commits are adequate for the immediate demo; a push can happen through an already-authorized path later.
- **The host is Bitrig-only, with no local build/export tools or agent tools:** execute the same role packets sequentially inside its supported project and disclose that mode. Do not promise shared local editing, Xcode verification, or three workers. If native Duo build/run is also unavailable, report the exact capability blocker; continue asset/spec preparation where useful, but do not claim a running native demo.
- **Authentication or import needs human action:** identify that exact action and continue independent local work. Do not repeatedly ask for permission to build, test, commit, or continue already-authorized milestones.

One paste can define a capability-aware workflow. It cannot autonomously bridge a missing tool, account permission, or cross-application channel. That limitation must appear in the master rather than emerge as a surprise after generation begins.

## How parallel components compile together

1. **One baseline first, with a hard timebox.** Coordinator creates one native target, app entry, the smallest necessary contracts, integration composition, and neutral A/B/C modules, plus test target membership. Every predeclared file is already in the appropriate target. Target a compiling baseline within 15 minutes; defer nonessential abstractions and diagnostics instead of building a framework. Baseline launches a primitive scene. Workers do not each scaffold an app. Do not introduce separate packages or a large dependency graph to make three workers appear independent.
2. **Prove membership before assuming it.** Determine whether the project uses synchronized source folders or explicit file references. Compile one harmless file in each worker folder and verify one approved WAV in the built bundle. Explicit projects require coordinator additions for every new file. Synchronized folders still need correct exceptions so documentation, sources, and tests do not enter the app target.
3. **Track the preparation baseline.** Preserve preexisting untracked files. Make the agreed preparation and scaffold available in Git before branching, so all worktrees contain the same docs, contracts, placeholders, and resources. Do not branch from `efa735e` and assume untracked preparation will appear.
4. **Use three isolated worktrees when supported.** Coordinator keeps the canonical integration checkout. Each worker uses its own branch/worktree created from the same recorded scaffold commit, with a separate derived build output directory. Workers never change the branch checked out in another worktree, run repository-wide cleanup, or share the integration Git index. A Git worktree is a separate checkout, not an automatically synchronized view of Codex or Bitrig.
5. **Fallback for shared filesystem agents.** If agent tooling shares one checkout and isolated worktrees are unavailable, keep exclusive source ownership and coordinator-only Git/build configuration. Workers deliver paused file changes; coordinator stages exact paths only. Never let workers independently commit the whole shared working tree or use broad add/reset/stash operations. Simulator ownership remains unchanged.
6. **Compile complete modules early.** Worker A first delivers a live-input/primitive-render slice, B a minimal controllable world with reset, and C primitive corgi/HUD plus silent feedback. Each is independently compilable against unchanged neutral versions of the other two. Workers submit small exact commits or scoped file deliveries every 10–20 minutes; an unfinished file is not a handoff.
7. **Integrate immutable deliveries serially.** Worker pauses, reports base/delivery SHA and exact paths. Coordinator reviews the diff, accepts only owned paths, integrates one delivery, compiles the whole app, and performs the relevant smoke check before accepting the next. An integration failure is assigned to its owner immediately; a working previous revision stays available. Coordinator never waits until all three modules are “finished” to discover an interface mismatch.
8. **Refresh safely.** Coordinator publishes the new integration revision after each green slice. Workers incorporate that revision in their own checkout only while paused and verify their branch still builds. Do not rebase, cherry-pick, or switch another worker's checkout behind its back. Shared contract changes require an explicit short synchronization window.
9. **Make target changes a coordinator transaction.** New source/resource filenames are requested in the handoff. Coordinator updates membership, then builds and checks the compiled bundle. Xcode project diffs, binary assets, lockfiles, and asset catalog entries are never “resolved later” with blind conflict selection.
10. **One release artifact.** Only the coordinator's integration checkout produces the simulator demo build and evidence. A worker's successful isolated build is useful, but it is not proof of the combined app. Record the exact launched revision and verify the working tree is accounted for.

No new package dependency, engine switch, app target, second physics world, or project regeneration may be introduced by a worker. Raise a concrete blocker with evidence; the coordinator chooses the smallest change and owns cross-cutting edits.

## Required worker handoff format

Each handoff must contain these fields in ordinary readable text:

- Worker and current status: ready for integration, blocked, or still in progress; whether editing is paused.
- Base integration revision and exact delivery revision; for shared-checkout mode, exact changed paths and coordinator-observed diff instead.
- Owned files changed, plus any accidental out-of-scope edit explicitly called out before integration.
- Behavior now available, stated in player-visible terms.
- Shared contracts used and any requested changes; “none” when unchanged.
- New target membership or resource requests; exact filename, source path, intended bundle path, and license/source where relevant.
- Build/test run: exact checkout, target/scheme, SDK/destination or test environment, result, and evidence/log location.
- What was observed on the actual simulator versus unit-tested, replayed, mocked, or not tested.
- One exact integration/simulator smoke scenario and expected result.
- Known defects and the next smallest useful delivery.
- Confirmation that the worker did not control shared simulator UI, modify project configuration, start another simulation loop, or change others' files.

The coordinator can accept a partial feature only if its delivery is compilable and leaves the previous working flow intact. “Looks good” and generated screenshots are not build evidence.
